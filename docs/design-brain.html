Anderdingus decision engine

Draft v2 for review, 2026-11-13. Not pushed. Rewritten after your explanation: a catalog of in-game situations, standard decision-tree inputs and outputs, and a model that only chooses.

What you described

A database of situations that happen in a round (enemy in front, teammate died, red radar blip). Each situation has standard inputs and a fixed set of possible outputs. A decision model picks one output; it never writes free-form text. Example: I'm on B, a teammate dies mid, I get told where they died and other relevant positions.

The pipeline

Sources
GSI, console, teammates→ Situation detector
catalog entries→ Decision
tree, later model→ Output template
fixed wording→ Discord
  • Situation catalog: each entry names the situation, its inputs (fields with types), the data source, and when it fires.
  • Decision catalog: each situation lists its allowed outputs (callout IDs with templates). Nothing outside the list can be said.
  • Decider: one interface, decide(situation, inputs) → output ID. Version 1 is a hand-written decision tree. Later a small model implements the same interface and is checked against the tree on recorded games.
  • Decision log: every situation, its inputs and the chosen output is saved (sanitized). That becomes training and test data for the model.

"Enemy in front" and "red radar blip" can't come from official data for a normal player. They would need on-screen reading (the deferred vision spike) and a rules check, because live enemy info is the riskiest kind of assistance.

Two pieces we must build

  1. Map zones. GSI gives coordinates, not names like "Mid" or "B site". CS2 already has place names (it shows your current place on the HUD radar), so we should reuse the game's own names rather than invent them. Options, best first, each to verify:
    • Extract place areas from the map's navigation data in the game files, giving coordinates → place name for free.
    • Read place tags from the console (team chat lines may carry the sender's place).
    • Fallback: hand-made zone polygons per map, using the game's place names.
    Reading the on-screen name directly would be vision work, so it waits for that spike. Start with Inferno.
  2. Own position check. GSI has a player_position section we don't request yet. Add it to the cfg, record a round, and confirm it reports position while you play, not just while spectating. The whole "where did my teammate die" idea depends on this.

What one catalog entry looks like

situation: teammate_died
inputs:
  victim: player_id
  victim_zone: zone      # from victim's position + map zones
  my_zone: zone
  alive_teammates: int
  round_time_left: seconds
outputs:
  - id: died_near_you     say: "{victim} died {victim_zone}, close to you"
  - id: died_far          say: "{victim} died {victim_zone}"
  - id: last_alive        say: "{victim} died {victim_zone}. You're last alive"
decider v1 (tree):
  alive_teammates == 0          → last_alive
  victim_zone adjacent my_zone  → died_near_you
  else                          → died_far

The decision model

  • Treated as a classifier: given the inputs, choose one output ID. Small, fast and checkable.
  • Candidates: a small local language model forced to answer with one listed ID, or a tiny trained classifier (for example a decision forest) built from the decision log. The second may beat a language model here and needs no GPU.
  • Any answer that isn't a listed ID is dropped and the tree's answer is used.

How the decision database gets built

Claude Code does not write catalog entries itself. It acts as the orchestrator: it owns the format, the checks and the merge, and it hands the authoring to subagents.
Role Does Doesn't
Orchestrator (Claude Code) Writes the catalog schema, validator and tests. Splits the work into slices. Briefs agents, validates what comes back, resolves conflicts, opens PRs. Author situation or decision entries.
Author agents Each writes entries for one slice (for example: bomb situations, own-state situations, teammate situations, Inferno zones). Output must pass the validator. Change the schema, invent data sources, or add enemy-position situations.
Reviewer agent Checks each slice against the integrity rules, the data-availability table and duplicate or conflicting entries. Edit entries; it reports findings only.
Owner (you) Approves the schema before agents start, and approves each slice's PR. -

Guardrails: every entry must name a data source marked available; blocked situations are listed as blocked, not authored. At most 4 author agents per batch, on a cheaper model where quality allows. Each slice lands as its own small PR. Agents get the schema and source table, not this whole conversation.

Proposed order

  1. Position check: add player_position to the cfg, record a round, confirm.
  2. Schema and engine (orchestrator): catalog schema, validator, tree decider interface, decision log. You approve the schema.
  3. First authoring batch (agents): entries that work on your data alone (bomb, own state, round flow), plus Inferno zones. Reviewer agent, then one PR per slice.
  4. Team sprint: teammates' companions share state, unlocking "teammate died" with location.
  5. Model spike: train or prompt a chooser against the decision log, compare with the tree.
